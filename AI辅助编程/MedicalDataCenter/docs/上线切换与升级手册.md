# 医疗数据中心上线切换与升级手册

## 1. 文档目标

本文档用于指导 `MedicalDataCenter` 在以下场景下的上线与升级操作：

- 新环境首次安装
- 存量环境升级到当前版本
- 发布窗口内的切换执行
- 发布失败后的回滚与恢复
- 发布后的验收与观察

本文档强调“可执行顺序”和“风险控制”，默认适用于当前项目的 Docker 生产版部署方式。

## 2. 适用范围

当前手册适用于：

- 部署编排：`docker/docker-compose.prod.yml`
- 应用配置：`docker/.env.prod`
- 数据库迁移版本：`V1 -> V13`
- 后端运行模式：`Spring Boot + Flyway 自动迁移`
- 前端接入方式：`Nginx HTTPS 统一入口`

## 3. 角色分工建议

建议上线时至少明确以下角色：

| 角色 | 职责 |
| --- | --- |
| 发布负责人 | 统一指挥、确认窗口、推进执行、记录结果 |
| 应用执行人 | 执行 Docker、镜像、配置、服务启停操作 |
| DBA/数据负责人 | 备份数据库、确认迁移策略、处理 SQL 异常 |
| 验证负责人 | 登录验收、接口验收、业务路径验证 |

如果是单人执行，也建议按上述角色思路拆分步骤，不要把“备份、升级、验证”混在一起一次性操作。

## 4. 上线前准备

### 4.1 必备输入

在上线前请确认以下内容已准备完成：

- 已确认本次目标版本和代码分支
- 已确认 `docker/.env.prod` 最终值
- 已确认 HTTPS 证书 `docker/certs/tls.crt` 与 `docker/certs/tls.key`
- 已确认数据库连接、业务账号和 Redis 密码
- 已确认发布窗口和回滚窗口
- 已确认负责验收的人员可在发布后立即验证

### 4.2 配置核对清单

建议重点核对以下变量：

| 配置项 | 说明 |
| --- | --- |
| `MDC_DB_NAME` | 业务数据库名 |
| `MDC_DB_USERNAME` | 业务数据库用户 |
| `MDC_DB_PASSWORD` | 业务数据库密码 |
| `REDIS_PASSWORD` | Redis 密码 |
| `MDC_HTTP_PORT` | HTTP 入口端口 |
| `MDC_HTTPS_PORT` | HTTPS 入口端口 |
| `MDC_JWT_SECRET` | 当前 JWT 密钥 |
| `MDC_JWT_ACTIVE_KID` | 当前 JWT `kid` |
| `MDC_JWT_PREVIOUS_SECRETS` | 历史 JWT 密钥 |
| `MDC_OAUTH2_ISSUER` | 生产签发方，必须为 HTTPS 地址 |
| `MDC_ALLOWED_ORIGIN_PATTERNS` | 允许来源 |
| `MDC_AES_KEY` | 当前 AES 密钥 |
| `MDC_AES_ACTIVE_KEY_VERSION` | 当前 AES 密钥版本 |
| `MDC_AES_PREVIOUS_KEYS` | 历史 AES 密钥 |

### 4.3 风险提醒

上线前请明确以下事实：

- 当前后端启动时会自动执行 Flyway
- 如果数据库版本有变化，本次发布可能伴随结构迁移
- 原生 SQL 手工执行模式不会自动维护 `flyway_schema_history`
- 生产版后端不直接对外暴露 `18080`
- 发布成功后的验收入口应走 `https://mdc.localtest.me:18443/` 或你的正式域名

## 5. 上线策略选择

### 5.1 推荐策略

当前项目推荐采用以下策略：

- 新环境首次安装：自动模式
- 小版本常规升级：自动模式
- 数据库异常修复：人工审慎介入
- 离线升级：优先 Flyway CLI，次选手工 SQL

### 5.2 自动模式

适用场景：

- 全新环境
- 现有环境从已知稳定版本升级到当前版本
- Flyway 可以正常接管数据库变更

特点：

- 由 `tidb-init` 自动建库和授权
- 由 Spring Boot + Flyway 自动执行迁移
- 操作最少，出错面最小

### 5.3 手工模式

适用场景：

- 需要由 DBA 预建库和预授权
- 不允许应用首次启动自动迁移
- 某次迁移中断，需要人工排障
- 数据库已被手工修改，需要显式核对版本状态

特点：

- 执行前必须先备份
- 必须记录执行顺序
- 推荐优先使用 Flyway CLI

## 6. 新环境首次安装

### 6.1 执行顺序

新环境首次安装推荐按以下顺序执行：

1. 准备代码和配置文件
2. 配置 `.env.prod`
3. 准备证书
4. 启动生产版编排
5. 确认 `tidb-init`
6. 确认 `backend` Flyway 完成
7. 确认 `frontend` 正常提供 HTTPS
8. 执行登录与接口验收

### 6.2 操作命令

```powershell
cd E:\trae_learning\MedicalDataCenter
Copy-Item .\docker\.env.prod.example .\docker\.env.prod
pwsh .\scripts\generate-localtest-cert.ps1 -Trust
docker compose -f .\docker\docker-compose.prod.yml --env-file .\docker\.env.prod up -d --build
docker compose -f .\docker\docker-compose.prod.yml --env-file .\docker\.env.prod ps
docker compose -f .\docker\docker-compose.prod.yml --env-file .\docker\.env.prod logs --tail=200 tidb-init
docker compose -f .\docker\docker-compose.prod.yml --env-file .\docker\.env.prod logs --tail=200 backend
docker compose -f .\docker\docker-compose.prod.yml --env-file .\docker\.env.prod logs --tail=200 frontend
```

### 6.3 首次安装成功标准

以下条件同时满足，可视为首次安装成功：

- `tidb` 为 `healthy`
- `tidb-init` 退出成功
- `backend` 无 Flyway 报错
- `frontend` 无证书和 Nginx 报错
- 首页可访问
- 默认管理员可登录
- 健康检查接口返回正常

## 7. 存量环境升级

### 7.1 升级前检查

在升级前，必须先确认：

- 当前线上运行版本
- 当前数据库最大迁移版本
- 当前 `.env.prod` 是否与目标版本兼容
- 当前证书文件是否仍有效
- 当前是否存在未完成的调度任务或重要导出

推荐检查项：

```powershell
docker compose -f .\docker\docker-compose.prod.yml --env-file .\docker\.env.prod ps
docker compose -f .\docker\docker-compose.prod.yml --env-file .\docker\.env.prod logs --tail=200 backend
```

数据库建议检查：

```sql
SELECT * FROM flyway_schema_history ORDER BY installed_rank;
SELECT id, template_id, template_version, enabled FROM report_schedule ORDER BY id;
SELECT id, schedule_id, template_version, created_at FROM report_snapshot ORDER BY id DESC LIMIT 20;
```

### 7.2 升级前备份

升级前至少执行以下备份：

- TiDB 业务数据库备份
- `.env.prod` 备份
- `docker/certs/` 证书目录备份
- `backend-exports` 导出目录备份

如果条件允许，建议额外保留：

- 当前镜像标签
- 当前发布日志
- 当前容器状态截图或 `ps` 输出

### 7.3 推荐升级路径

当前版本推荐路径：

1. 备份
2. 拉取或切换到目标代码
3. 校验配置文件
4. 执行 `docker compose up -d --build`
5. 观察 `backend` Flyway 日志
6. 进行验收

### 7.4 常规升级命令

```powershell
cd E:\trae_learning\MedicalDataCenter
docker compose -f .\docker\docker-compose.prod.yml --env-file .\docker\.env.prod up -d --build
docker compose -f .\docker\docker-compose.prod.yml --env-file .\docker\.env.prod ps
docker compose -f .\docker\docker-compose.prod.yml --env-file .\docker\.env.prod logs --tail=200 backend
docker compose -f .\docker\docker-compose.prod.yml --env-file .\docker\.env.prod logs --tail=200 frontend
```

### 7.5 升级成功标准

升级成功至少满足：

- `backend` 和 `frontend` 都已启动
- Flyway 已执行完成
- 健康检查通过
- 登录正常
- 报表预览正常
- 开放 API 可正常取 token 并返回数据

## 8. 数据库升级策略

### 8.1 自动迁移模式

这是默认推荐模式。

执行逻辑：

1. 应用启动
2. Flyway 读取 `flyway_schema_history`
3. 找到未执行版本
4. 按 `V1 -> V13` 顺序补齐
5. 记录迁移历史

适用于：

- 数据库历史清晰
- 未被人工绕开 Flyway 修改
- 当前版本和目标版本迁移顺序正常

### 8.2 Flyway CLI 模式

当不希望由应用首次启动触发迁移时，可使用 Flyway CLI：

```powershell
flyway -url="jdbc:mysql://127.0.0.1:4000/medical_data_center" -user=mdc_app -password=你的密码 -locations="filesystem:.\backend\src\main\resources\db\migration" migrate
```

优点：

- 保留迁移历史
- 执行顺序清晰
- 适合由 DBA 或运维提前控制

### 8.3 原始 SQL 模式

只有在特殊排障时才建议使用。

执行原则：

- 必须严格按 `V1 -> V13`
- 必须记录人工执行结果
- 执行后要考虑 Flyway 历史和数据库实际状态的一致性

不建议作为常规上线模式。

## 9. 切换窗口操作手册

### 9.1 发布窗口前 30 分钟

建议完成：

1. 锁定发布版本
2. 通知验证人员待命
3. 导出并备份当前配置
4. 备份数据库和导出目录
5. 确认当前系统健康

### 9.2 发布窗口开始

建议顺序：

1. 停止外部变更操作
2. 保留当前容器状态记录
3. 启动目标版本镜像
4. 观察迁移日志
5. 核对服务状态

### 9.3 发布后 10 分钟内

必须完成以下检查：

- 首页访问
- 管理员登录
- `actuator/health`（仅部署机本机执行）
- `/oauth2/token`
- `/open-api/v1/patients`
- 报表预览
- 报表调度列表查询

## 10. 回滚策略

### 10.1 回滚原则

当前项目回滚需要区分两类：

- 应用层回滚
- 数据库层回滚

应用层回滚相对容易，数据库层回滚必须谨慎。

### 10.2 应用层回滚

适用场景：

- 数据库未发生不可逆变化
- 仅前端或后端业务逻辑异常
- 配置或 Nginx 配置错误

执行建议：

1. 切回上一版本代码或镜像
2. 恢复上一版 `.env.prod`
3. 重新 `docker compose up -d --build`
4. 再次验证入口可用

### 10.3 数据库层回滚

适用场景：

- 迁移失败导致结构不一致
- 迁移成功但业务验证失败，且变更不可兼容

执行建议：

1. 停止应用写入
2. 恢复上线前数据库备份
3. 恢复匹配该数据库版本的应用镜像
4. 恢复配置
5. 重新启动并验证

注意：

- 不建议通过“手工写反向 SQL”作为默认回滚方案
- 当前更可靠的方式仍是“数据库备份恢复 + 应用版本回退”

## 11. 备份与恢复建议

### 11.1 最小备份集

每次上线前至少备份：

- 业务数据库
- `.env.prod`
- `docker/certs/`
- `backend-exports`

### 11.2 恢复顺序

恢复时建议按以下顺序：

1. 恢复数据库
2. 恢复配置文件
3. 恢复证书
4. 恢复导出目录
5. 切回匹配应用版本
6. 启动服务并验收

## 12. 上线后验收清单

### 12.1 基础验收

- 前端首页可打开
- 登录成功
- 健康检查通过
- 菜单权限正常

### 12.2 业务验收

- 数据源页面可正常打开
- ETL 页面可正常查询任务
- 数据集页面可查看样本
- 报表设计器可打开模板
- 报表任务页可查看调度和快照

### 12.3 接口验收

- `/oauth2/token` 可申请 token
- `/open-api/v1/patients` 正常返回
- `/open-api/v1/encounters` 正常返回
- `/open-api/v1/labs` 正常返回
- `/open-api/v1/medications` 正常返回

### 12.4 版本与调度验收

- `report_schedule.template_version` 存在合理值
- `report_snapshot.template_version` 存在合理值
- 报表调度未因版本不一致异常堆积

## 13. 失败排障顺序

若发布失败，建议按以下顺序排查：

1. 看 `docker compose ps`
2. 看 `tidb-init` 日志
3. 看 `backend` 日志
4. 看 `frontend` 日志
5. 看数据库 `flyway_schema_history`
6. 看 `sys_audit_log` 和 `api_access_log`

推荐命令：

```powershell
docker compose -f .\docker\docker-compose.prod.yml --env-file .\docker\.env.prod ps
docker compose -f .\docker\docker-compose.prod.yml --env-file .\docker\.env.prod logs --tail=200 tidb-init
docker compose -f .\docker\docker-compose.prod.yml --env-file .\docker\.env.prod logs --tail=200 backend
docker compose -f .\docker\docker-compose.prod.yml --env-file .\docker\.env.prod logs --tail=200 frontend
```

## 14. 推荐发布记录模板

每次上线建议至少记录：

- 发布时间
- 发布负责人
- 目标版本
- 配置变更项
- 数据库版本变化
- 是否执行备份
- 是否执行回滚
- 验收结果
- 异常说明

## 15. 结论

当前项目最推荐的上线方式是：

- 生产版 Compose 部署
- `tidb-init + Flyway` 自动迁移
- 上线前强制备份
- 上线后立即执行验收
- 异常时优先采用“恢复数据库备份 + 回退应用版本”

这比手工逐条执行 SQL 更安全，也更符合当前项目的工程化交付方式。
