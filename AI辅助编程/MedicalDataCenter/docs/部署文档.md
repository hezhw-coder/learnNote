# 医疗数据中心部署文档

## 1. 文档目标

本文档用于指导当前 `MedicalDataCenter` 项目在本地开发、演示验证和本机生产化模拟场景下完成部署、启停和排障。当前交付已覆盖：

- 前端 `Vite + Vue + TypeScript`
- 后端 `Spring Boot + Maven`
- `TiDB + Redis + Nginx` 容器编排
- `Flyway V1 -> V13` 线性迁移
- 生产版 HTTPS、本地自签名证书和安全基线变量

配套文档建议一起阅读：

- 架构总览见 [架构设计文档.md](file:///e:/trae_learning/MedicalDataCenter/docs/%E6%9E%B6%E6%9E%84%E8%AE%BE%E8%AE%A1%E6%96%87%E6%A1%A3.md)
- 上线执行与回滚流程见 [上线切换与升级手册.md](file:///e:/trae_learning/MedicalDataCenter/docs/%E4%B8%8A%E7%BA%BF%E5%88%87%E6%8D%A2%E4%B8%8E%E5%8D%87%E7%BA%A7%E6%89%8B%E5%86%8C.md)

## 2. 当前部署模式

项目同时维护两套 Compose 编排：

| 模式 | 编排文件 | 适用场景 | 外部暴露 |
| --- | --- | --- | --- |
| 开发版 | `docker/docker-compose.yml` | 日常联调、接口调试 | 前端 `18081`，后端 `18080` |
| 生产版 | `docker/docker-compose.prod.yml` | 本机生产化验证、HTTPS 演示 | Nginx `18081/18443`，后端不直接暴露 |

当前生产版拓扑如下：

| 组件 | 服务名 | 端口/方式 | 说明 |
| --- | --- | --- | --- |
| Nginx + 前端静态资源 | `frontend` | `18081 -> 80`，`18443 -> 443` | 统一提供页面、反代 `/api`、`/oauth2`、`/open-api`、`/actuator` |
| Spring Boot 后端 | `backend` | 仅容器内 `8080` | 提供管理 API、开放 API、调度、导出、健康检查 |
| TiDB | `tidb` | 容器内 `4000/10080` | 主业务库 |
| TiDB 初始化 | `tidb-init` | 无 | 自动建库、建应用账号、授权 |
| Redis | `redis` | 容器内 `6379` | 会话、限流、缓存 |

注意：

- 生产版下宿主机不能直接访问 `127.0.0.1:18080`，因为 `backend` 未映射端口。
- 生产版所有外部访问都应通过 `frontend` Nginx 入口完成。

## 3. 前置条件

部署前请准备：

- `Docker Desktop 24+`
- `Docker Compose v2+`
- 至少 `4 CPU / 8 GB RAM / 30 GB` 可用磁盘
- 可正常拉取 `pingcap/tidb`、`redis`、`mysql`、`nginx`、JDK/Node 基础镜像

如需在宿主机执行源码测试或构建，另需准备：

- 前端：`Node.js 20+`、`npm 10+`
- 后端：`JDK 17`、`Maven 3.9+`

## 6. 首次准备

### 6.1 生成本机自签名证书

如需本机 HTTPS 演示，先生成证书：

```powershell
pwsh .\scripts\generate-localtest-cert.ps1 -Trust
```

执行成功后，应生成：

- `docker/certs/tls.crt`
- `docker/certs/tls.key`

### 6.2 可选的源码预构建

如需先在宿主机验证源码，可执行：

```powershell
pwsh -File .\scripts\build.ps1
```

说明：

- 前端会执行 `npm install` 和 `npm run build`
- 后端会执行 `mvn clean package -DskipTests`
- 容器构建本身也支持在镜像内完成构建，不强依赖宿主机已安装 Maven

### 6.3 数据库初始化策略

当前项目数据库初始化存在两种模式：

| 模式 | 是否推荐 | 适用场景 | 是否需要手工执行 SQL |
| --- | --- | --- | --- |
| 自动模式 | 推荐 | Docker 开发版、Docker 生产版、标准本地演示 | 否 |
| 手工模式 | 仅在特殊场景使用 | 无法通过应用自动迁移、离线升级、Flyway 修复、人工接管数据库初始化 | 是 |

正常情况下：

- `tidb-init` 会自动创建数据库、应用账号和授权
- Spring Boot 启动后会自动执行 `Flyway V1 -> V13`
- 不需要手工逐条执行 SQL

只有在以下情况才建议手工执行：

- 你不使用 Docker 中的 `tidb-init`
- 需要先由 DBA 预建库和授权
- 应用因迁移中断，需要人工补齐数据库版本
- 存量环境做离线升级，不允许应用首次启动时直接迁移

所有命令都应在项目根目录执行：

```powershell
E:\trae_learning\MedicalDataCenter
```

### 7.1 启动开发版

```powershell
docker compose -f .\docker\docker-compose.yml up -d --build
```

### 7.2 启动生产版

```powershell
docker compose -f .\docker\docker-compose.prod.yml --env-file .\docker\.env.prod up -d --build
```

如需强制刷新容器：

```powershell
docker compose -f .\docker\docker-compose.prod.yml --env-file .\docker\.env.prod up -d --build --force-recreate
```

首次启动时系统会自动完成：

- 启动 `TiDB`、`Redis`
- `tidb-init` 自动创建数据库与应用账号
- 后端执行 `Flyway` 迁移，当前顺序为 `V1 -> V13`
- 前端 Nginx 加载静态资源并反向代理统一入口

### 7.3 推荐启动顺序

建议按以下顺序执行和确认：

1. 准备 `.env.prod`
2. 生成或确认 HTTPS 证书
3. 启动 `docker-compose.prod.yml`
4. 确认 `tidb` 和 `tidb-init` 成功
5. 确认 `backend` 启动并完成 Flyway
6. 确认 `frontend` 启动
7. 访问 `https://mdc.localtest.me:18443/`

推荐检查命令：

```powershell
docker compose -f .\docker\docker-compose.prod.yml --env-file .\docker\.env.prod ps
docker compose -f .\docker\docker-compose.prod.yml --env-file .\docker\.env.prod logs --tail=200 tidb-init
docker compose -f .\docker\docker-compose.prod.yml --env-file .\docker\.env.prod logs --tail=200 backend
docker compose -f .\docker\docker-compose.prod.yml --env-file .\docker\.env.prod logs --tail=200 frontend
```

### 7.4 首次启动成功标准

以下条件同时满足时，可视为生产版启动成功：

- `tidb` 状态为 `healthy`
- `tidb-init` 正常退出，退出码为 `0`
- `backend` 日志中未出现 Flyway 报错
- `frontend` 日志中未出现证书或 Nginx 配置错误
- `curl.exe -k https://mdc.localtest.me:18443/actuator/health` 返回健康响应

## 8. 数据库初始化与 SQL 执行说明

### 8.1 正常情况哪些 SQL 需要手工执行

结论：

- 正常 Docker 启动场景下，不需要手工执行任何业务表 SQL
- 数据库建库、建用户、授权由 `tidb-init` 自动完成
- 表结构和种子数据由 Flyway 自动完成

也就是说，默认不需要手工执行：

- `V1__init_schema.sql`
- `V2__seed_demo_patients_and_report.sql`
- ...
- `V13__track_report_template_version_on_schedule_and_snapshot.sql`

### 8.2 自动执行顺序

自动模式下实际执行顺序如下：

1. `tidb-init` 执行建库和授权 SQL
2. `backend` 启动
3. Flyway 自动按版本顺序执行 `V1 -> V13`
4. 应用继续初始化 Quartz、缓存和业务服务
5. `frontend` 通过 Nginx 提供统一入口

### 8.3 `tidb-init` 自动执行的基础 SQL

如果你不用容器自动初始化，而是要手工预建库和账号，可按以下 SQL 执行：

```sql
CREATE DATABASE IF NOT EXISTS `medical_data_center` DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_bin;
CREATE USER IF NOT EXISTS 'mdc_app'@'%' IDENTIFIED BY '请替换为你的密码';
ALTER USER 'mdc_app'@'%' IDENTIFIED BY '请替换为你的密码';
GRANT ALL PRIVILEGES ON `medical_data_center`.* TO 'mdc_app'@'%';
```

说明：

- 上面是 `tidb-init` 的逻辑等价写法
- 实际数据库名、用户名、密码应以 `.env.prod` 为准
- 若你改了环境变量，请同步替换 SQL 里的库名和用户

### 8.4 Flyway 迁移 SQL 执行顺序

如果必须手工执行迁移脚本，必须严格按以下顺序：

| 顺序 | SQL 文件 | 作用 |
| --- | --- | --- |
| 1 | `V1__init_schema.sql` | 初始化核心表、管理员账号、基础权限、基础数据集、默认 API 范围 |
| 2 | `V2__seed_demo_patients_and_report.sql` | 初始化演示患者数据和基础报表数据 |
| 3 | `V3__open_api_and_system_alignment.sql` | 补齐开放 API 和系统管理相关结构/数据 |
| 4 | `V4__expand_etl_subject_with_lab_result.sql` | 新增检验结果相关标准主题与配套元数据 |
| 5 | `V5__complete_system_role_and_param_management.sql` | 完善角色、权限、系统参数能力 |
| 6 | `V6__auth_session_and_security_hardening.sql` | 引入服务端会话、安全字段与密码失败控制 |
| 7 | `V7__report_schedule_quartz_automation.sql` | 增加报表调度自动化和 Quartz 相关表结构 |
| 8 | `V8__expand_etl_subject_with_medication_order.sql` | 新增用药医嘱主题 |
| 9 | `V9__enhance_open_api_filters_and_medication_scope.sql` | 增强开放 API 筛选和用药 scope |
| 10 | `V10__security_rotation_audit_and_secret_hosting.sql` | 新增安全轮换与审计增强字段 |
| 11 | `V11__standardize_etl_field_bindings_storage.sql` | 为 ETL 增加 `field_bindings_json` |
| 12 | `V12__parameterize_report_exports_and_schedules.sql` | 为报表调度/快照增加 `runtime_params_json` |
| 13 | `V13__track_report_template_version_on_schedule_and_snapshot.sql` | 为报表调度/快照增加 `template_version` |

### 8.5 手工执行 SQL 的推荐顺序

若你要完全手工初始化数据库，推荐顺序如下：

1. 使用 root 或管理员账号连接 TiDB
2. 执行建库和授权 SQL
3. 优先选择 `Flyway CLI` 按版本执行迁移，保证 `flyway_schema_history` 正常记录
4. 若只能用原生 SQL，则切换到业务库后依次执行 `V1 -> V13`
5. 校验迁移记录或至少校验业务表是否完整
6. 再启动后端应用

注意：

- 不要跳版本执行
- 不要先执行高版本再回补低版本
- 不要在 Flyway 自动执行后再重复手工执行同一份 SQL
- 若采用原生 SQL 直接执行，后续仍需考虑如何让 Flyway 历史与数据库实际状态保持一致

### 8.6 手工执行示例

推荐优先使用 Flyway 工具执行迁移，这样可以保留 `flyway_schema_history`：

```powershell
flyway -url="jdbc:mysql://127.0.0.1:4000/medical_data_center" -user=mdc_app -password=你的密码 -locations="filesystem:.\backend\src\main\resources\db\migration" migrate
```

若当前环境只能用 TiDB/MySQL 客户端执行原始 SQL，可参考：

```powershell
mysql -h 127.0.0.1 -P 4000 -u root
```

进入后执行：

```sql
CREATE DATABASE IF NOT EXISTS `medical_data_center` DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_bin;
CREATE USER IF NOT EXISTS 'mdc_app'@'%' IDENTIFIED BY '你的密码';
ALTER USER 'mdc_app'@'%' IDENTIFIED BY '你的密码';
GRANT ALL PRIVILEGES ON `medical_data_center`.* TO 'mdc_app'@'%';
USE medical_data_center;
```

随后按文件顺序执行：

```powershell
mysql -h 127.0.0.1 -P 4000 -u mdc_app -p medical_data_center < .\backend\src\main\resources\db\migration\V1__init_schema.sql
mysql -h 127.0.0.1 -P 4000 -u mdc_app -p medical_data_center < .\backend\src\main\resources\db\migration\V2__seed_demo_patients_and_report.sql
...
mysql -h 127.0.0.1 -P 4000 -u mdc_app -p medical_data_center < .\backend\src\main\resources\db\migration\V13__track_report_template_version_on_schedule_and_snapshot.sql
```

原始 SQL 模式的注意事项：

- 这种方式不会自动写入 `flyway_schema_history`
- 后续若直接启动带 Flyway 的应用，Flyway 仍会尝试重新执行迁移
- 因此原始 SQL 模式仅适合临时排障、离线初始化或 DBA 接管场景

### 8.7 哪些 SQL 不建议手工执行

以下场景不建议手工执行 SQL：

- 通过 `docker-compose.prod.yml` 正常首次启动
- 仅仅是重新部署应用镜像
- 仅仅是调整前端配置或 Nginx 配置
- Flyway 已正常执行成功的环境

原因：

- 可能造成重复初始化
- 可能污染演示数据
- 可能让数据库状态和 `flyway_schema_history` 不一致

### 8.8 手工执行后的校验 SQL

如果你通过 Flyway CLI 执行，建议检查：

```sql
SHOW TABLES;
SELECT * FROM flyway_schema_history ORDER BY installed_rank;
SELECT username, enabled FROM sys_user;
SELECT code, name FROM meta_dataset ORDER BY code;
SELECT id, name, status FROM report_template ORDER BY id;
```

如果你通过原始 SQL 执行，建议检查：

```sql
SHOW TABLES;
SELECT username, enabled FROM sys_user;
SELECT code, name FROM meta_dataset ORDER BY code;
SELECT id, name, status FROM report_template ORDER BY id;
```

期望结果：

- 能看到核心表已创建
- 若使用 Flyway CLI，`flyway_schema_history` 中版本连续到 `13`
- 存在默认管理员 `admin`
- 能看到基础数据集和默认模板

## 11. 反向代理与安全基线

生产版 Nginx 配置位于 `docker/nginx/default.prod.conf`，当前已覆盖：

- `/` 单页应用入口
- `/api/` 管理端接口
- `/oauth2/` 令牌申请
- `/open-api/` 开放 API
- `/actuator/` 健康检查，仅部署机本机访问
- `HTTP -> HTTPS` 跳转
- `HSTS` 头与 `X-Forwarded-*` 标准转发

当前安全基线已包含：

- `prod` profile 启动前校验
- JWT 双密钥兼容验签与 `kid` 标识
- AES 历史密钥兼容解密
- 审计日志与开放 API 日志增加 `request_id`、来源 IP、UA、耗时
- 系统参数页禁止写入敏感密钥类参数

| `backend-exports` | 报表导出文件 |

建议：

- 定期归档 `backend-exports`
- 对 TiDB 和 Redis 做独立备份
- 在生产环境把 `docker/secrets` 替换为正式 Secret 托管方案

## 13. 故障排查

### 13.1 `.env.prod` 找不到

原因通常是命令不在项目根目录执行。

正确命令：

```powershell
cd E:\trae_learning\MedicalDataCenter
docker compose -f .\docker\docker-compose.prod.yml --env-file .\docker\.env.prod up -d --build
```

### 13.2 生产版 `curl http://127.0.0.1:18080/actuator/health` 失败

这是预期现象。生产版 `backend` 不暴露宿主机端口，应在部署机本机执行：

```powershell
curl.exe -k https://mdc.localtest.me:18443/actuator/health
```

### 13.3 HTTPS 无法访问

检查：

- `docker/certs/tls.crt`
- `docker/certs/tls.key`
- `docker/nginx/default.prod.conf`
- `.env.prod` 中 `MDC_HTTPS_PORT`

### 13.4 后端容器无法启动

重点检查：

- `tidb`、`tidb-init`、`redis` 是否正常
- `MDC_JWT_SECRET`、`MDC_AES_KEY`、`MDC_OAUTH2_ISSUER`、`MDC_ALLOWED_ORIGIN_PATTERNS` 是否满足 `prod` 校验要求
- `backend/src/main/resources/db/migration/` 是否保持 `V1 -> V13` 单线性顺序
- 若你采用手工模式，确认数据库已按 `V1 -> V13` 顺序执行完成
- 若你手工执行过部分 SQL，确认没有和 Flyway 自动迁移重复

推荐命令：

```powershell
docker compose -f .\docker\docker-compose.prod.yml --env-file .\docker\.env.prod logs --tail=200 backend
```

### 13.5 生产版页面可开但登录异常

检查：

- 是否通过 `https://mdc.localtest.me:18443/` 访问
- 浏览器是否残留旧 `localStorage`：`mdc-token`、`mdc-user`
- `frontend` 是否按最新 `default.prod.conf` 重建
- `backend` 是否按最新报表/认证代码重建

### 13.6 Flyway 或 CI 失败

检查：

- 后端：`mvn clean verify`
- 前端：`npm run check:ci`
- 覆盖率基线：
  - 后端 `LINE >= 10%`、`BRANCH >= 5%`
  - 前端 `statements/functions/lines >= 8%`、`branches >= 5%`
- `compose-smoke` 失败时优先查看 `.artifacts/compose-smoke/`

### 13.7 Flyway 中断后的人工修复建议

若 Flyway 在中途失败，建议按以下顺序处理：

1. 先备份数据库
2. 查看 `flyway_schema_history`
3. 确认最后一个成功版本
4. 根据失败点决定是修复 SQL 还是补执行缺失版本
5. 不要跳过失败版本直接执行更高版本
6. 修复后重新启动应用，让 Flyway 继续接管

仅当你确认完全理解数据库状态时，才建议人工补执行某个 `V*.sql`
