# 医疗数据中心架构设计文档

## 1. 文档目标

本文档基于当前 `MedicalDataCenter` 项目的实际实现，描述系统的总体架构、模块边界、关键数据流、部署形态、安全设计、数据模型和运维策略，用于支撑以下场景：

- 项目交付说明
- 新成员快速理解系统
- 环境部署与排障
- 后续迭代设计基线

本文档描述的是“当前已实现版本”，不是纯规划蓝图。

## 2. 建设目标

项目围绕医疗数据中心 MVP 的四类核心能力建设：

- 可视化数据源配置
- 多源医疗数据抽取与标准化
- 在线报表设计、导出与调度
- 面向第三方的开放 API 服务

在此基础上，项目已经补充以下工程化能力：

- RBAC 权限控制
- JWT/OAuth2 风格鉴权
- Redis 限流与缓存
- Quartz 调度
- Flyway 数据库迁移
- HTTPS/HSTS 与密钥轮换
- CI 与容器级 smoke 回归

## 3. 总体架构

### 3.1 技术栈

| 层级 | 技术选型 | 说明 |
| --- | --- | --- |
| 前端 | `Vite`、`Vue 3`、`TypeScript`、`Element Plus`、`Pinia`、`Vue Router`、`Vitest` | 管理控制台与低代码报表设计器 |
| 后端 | `Spring Boot 3`、`Spring Security`、`JdbcTemplate`、`Quartz`、`Flyway`、`JUnit 5` | 业务 API、调度、鉴权、迁移 |
| 数据库 | `TiDB` | 主业务数据、标准化数据、配置数据、审计日志 |
| 缓存/限流 | `Redis` | 限流、缓存、辅助状态 |
| 网关/静态资源 | `Nginx` | 承载前端静态资源、统一反向代理 |
| 容器编排 | `Docker Compose` | 开发版与生产版部署 |

### 3.2 逻辑分层

系统采用前后端分离架构，整体可分为 5 层：

1. 表现层
   - Vue 单页应用
   - 页面、表单、表格、图表、低代码设计器
2. 接入层
   - Nginx
   - HTTPS、静态资源服务、反向代理
3. 业务层
   - Spring Boot 各业务模块
   - 认证、系统管理、数据源、ETL、数据集、报表、开放 API
4. 数据与基础设施层
   - TiDB、Redis、Quartz、Flyway、文件导出目录
5. 运维治理层
   - 审计日志、请求 ID、容器健康检查、CI/smoke

### 3.3 运行时拓扑

生产版运行拓扑如下：

```text
Browser
  -> Nginx(frontend, 18443/18081)
     -> /            -> Vue SPA
     -> /api         -> Spring Boot backend
     -> /oauth2      -> Spring Boot backend
     -> /open-api    -> Spring Boot backend
     -> /actuator    -> Spring Boot backend

Spring Boot backend
  -> TiDB
  -> Redis
  -> Quartz Scheduler
  -> Export File Storage
```

说明：

- 生产版下后端不直接暴露宿主机端口
- 所有对外访问统一通过 Nginx 入口完成
- 这使前端、管理 API、开放 API、健康检查具备统一域名和安全头策略

## 4. 前端架构设计

### 4.1 页面组织

前端采用 `Vue Router + AppLayout` 组织页面，已落地页面包括：

- 登录页
- 工作台
- 数据源管理
- ETL 抽取集成
- 数据集管理
- 报表设计器
- 报表任务
- 开放 API
- 系统管理

路由均带 `requiresAuth` 和权限元信息，页面访问基于权限码动态控制。

### 4.2 状态管理

前端通过 `Pinia` 管理两类核心状态：

- 认证状态
  - token
  - 当前用户
  - 退出登录
  - 自动续期
- 权限状态
  - authority 列表
  - 菜单可见性
  - 路由访问控制

### 4.3 UI 结构

前端布局采用：

- 左侧导航菜单
- 顶部状态栏
- 主内容区域

当前导航已经支持：

- 菜单高亮
- 权限可见性过滤
- 折叠/展开

### 4.4 报表设计器前端模型

报表设计器是当前前端最复杂的子系统，已采用结构化 schema 驱动方式组织：

- `layout`
  - 画布列数、网格列数、行高、间距
- `widgets`
  - 图表/表格/指标卡组件
- `bindings`
  - 组件字段绑定
- `filters`
  - 模板级筛选条件
- `parameters`
  - 模板级运行时参数
- `interactions`
  - 组件联动规则
- `versioning`
  - 草稿、发布、生效版本元数据

当前设计器已具备：

- 24 栅格布局
- 组件排序、显隐、复制、删除
- 模板级参数定义
- 联动规则配置
- 保存草稿
- 发布模板
- 参数化预览与导出

## 5. 后端架构设计

### 5.1 模块划分

后端采用单体应用 + 模块化组织方式，核心模块包括：

| 模块 | 主要职责 |
| --- | --- |
| `common` | 统一响应、异常处理、请求上下文、请求 ID |
| `security` | Spring Security、JWT、CORS、请求过滤器 |
| `auth` | 登录、续期、退出、OAuth2 token、会话管理 |
| `system` | 用户、角色、权限、系统参数、审计日志 |
| `datasource` | 数据源配置、测试连接、启停状态 |
| `etl` | ETL 任务配置、执行、字段绑定、运行记录 |
| `warehouse` | 数据集元数据、样本预览、标准主题访问 |
| `report` | 模板、预览、导出、调度、快照、通知 |
| `openapi` | 客户端、作用域、限流、开放接口、访问日志 |
| `infrastructure` | 加解密等基础设施支撑 |

### 5.2 编程模型

当前后端主要使用以下模式：

- `Controller + Service` 合并在模块内部静态类组织
- `JdbcTemplate` / `NamedParameterJdbcTemplate` 直接访问数据库
- `record` 作为请求、响应和内部视图模型
- `Flyway` 管理数据库结构
- `Quartz` 管理调度任务

这种设计的优点是：

- 代码路径短
- 模块边界清晰
- 对 MVP 阶段快速交付足够高效

### 5.3 统一响应与异常

系统所有 API 统一返回：

- `code`
- `message`
- `data`
- `requestId`
- `timestamp`

异常统一由全局异常处理器拦截，业务异常返回明确的 HTTP 状态和错误信息。

### 5.4 认证与授权

管理端认证链路采用：

- 用户名密码登录
- 签发平台 `accessToken`
- 签发 `refreshToken`
- 服务端 `auth_session` 会话记录
- 退出登录时服务端撤销 session

开放 API 认证链路采用：

- `client_id/client_secret`
- OAuth2 风格 `/oauth2/token`
- 签发开放 API JWT
- 根据 scope 控制接口访问

权限控制采用两层机制：

- Spring Security 认证过滤
- 方法级 `@PreAuthorize` 权限校验

### 5.5 安全增强设计

当前已落地的安全能力包括：

- 请求级 `X-Request-Id`
- JWT `kid` 标识与历史密钥兼容验签
- AES 历史密钥兼容解密
- 严格 CORS 白名单
- 生产版 HTTPS 与 HSTS
- 系统参数禁止写入敏感密钥类内容
- 审计日志记录请求 ID、来源 IP、UA、耗时

## 6. 数据架构设计

### 6.1 数据分层

项目的数据处理链路采用以下分层：

1. 外部数据源
   - MySQL、TiDB、PostgreSQL 等业务系统
2. ODS 层
   - 保留抽取原始记录
3. CDM 层
   - 医疗标准主题数据
4. 元数据层
   - 数据集定义、字段定义
5. 应用配置层
   - 报表模板、调度、参数、开放 API 客户端、权限模型
6. 治理与日志层
   - 审计日志、访问日志、限流规则、系统参数

### 6.2 当前核心业务表

系统当前核心表大致分为以下几类：

- 身份与权限
  - `sys_user`
  - `sys_role`
  - `sys_permission`
  - `sys_user_role`
  - `sys_role_permission`
  - `auth_session`
- 数据源与 ETL
  - `ds_source`
  - `ds_source_secret`
  - `etl_job`
  - `etl_job_run`
  - `etl_increment_checkpoint`
  - `ods_record`
- 医疗主题数据
  - `cdm_patient`
  - `cdm_encounter`
  - `cdm_lab`
  - `cdm_lab_result`
  - `cdm_medication_order`
- 元数据
  - `meta_dataset`
  - `meta_dataset_field`
- 报表
  - `report_template`
  - `report_schedule`
  - `report_snapshot`
  - `notify_message`
- 开放 API
  - `api_client`
  - `api_scope`
  - `api_access_log`
  - `api_rate_limit_rule`
- 系统治理
  - `sys_audit_log`
  - `sys_parameter`

### 6.3 迁移管理

数据库结构由 Flyway 管理，当前版本顺序为：

1. `V1__init_schema.sql`
2. `V2__seed_demo_patients_and_report.sql`
3. `V3__open_api_and_system_alignment.sql`
4. `V4__expand_etl_subject_with_lab_result.sql`
5. `V5__complete_system_role_and_param_management.sql`
6. `V6__auth_session_and_security_hardening.sql`
7. `V7__report_schedule_quartz_automation.sql`
8. `V8__expand_etl_subject_with_medication_order.sql`
9. `V9__enhance_open_api_filters_and_medication_scope.sql`
10. `V10__security_rotation_audit_and_secret_hosting.sql`
11. `V11__standardize_etl_field_bindings_storage.sql`
12. `V12__parameterize_report_exports_and_schedules.sql`
13. `V13__track_report_template_version_on_schedule_and_snapshot.sql`

当前迁移策略是：

- 结构变更只通过 `V*__*.sql` 新增，不修改历史版本
- 新环境启动时自动全量迁移
- 存量环境升级时按版本顺序递增

## 7. 核心业务流程

### 7.1 登录与权限装载

1. 用户访问前端登录页
2. 前端调用 `/api/auth/login`
3. 后端校验用户、密码策略、锁定状态
4. 写入 `auth_session`
5. 签发平台 JWT 和 refresh token
6. 前端保存 token 和权限码
7. 路由与菜单基于权限码动态展示

### 7.2 数据源与 ETL 流程

1. 管理员配置数据源
2. 系统保存连接信息与加密后的密码
3. 数据工程师创建 ETL 任务
4. 配置目标标准主题和 `fieldBindings`
5. 执行 ETL
6. 原始数据写入 `ods_record`
7. 标准化写入对应 `cdm_*` 表
8. 记录运行结果和增量 checkpoint

### 7.3 报表设计与运行流程

1. 设计师选择数据集并配置模板
2. 保存 `design_json`
3. 配置模板级筛选、参数、联动、布局
4. 保存草稿
5. 预览时传入运行时参数
6. 后端统一解析模板并生成渲染结果
7. 导出 PDF/Excel 时复用同一渲染逻辑
8. 发布模板后调度可绑定模板版本执行

### 7.4 报表调度流程

1. 创建调度任务并配置 cron
2. Quartz 注册任务
3. 执行时读取模板和运行时参数
4. 若模板版本不一致则阻断
5. 生成快照与导出文件
6. 写入 `report_snapshot`
7. 写入站内通知

### 7.5 开放 API 流程

1. 管理员创建 API 客户端
2. 分配 scopes
3. 第三方调用 `/oauth2/token`
4. 后端校验 `client_id/client_secret`
5. 签发开放 API JWT
6. 第三方携带 Bearer token 调用 `/open-api/v1/*`
7. 系统做 scope 校验、限流、数据脱敏
8. 写入 `api_access_log`

## 8. 报表子系统设计

### 8.1 模板存储

报表模板主表为 `report_template`，关键字段包括：

- `name`
- `dataset_code`
- `design_json`
- `status`

其中 `design_json` 承载完整模板 schema，包括：

- 布局
- 组件
- 绑定
- 参数
- 联动
- 版本信息

### 8.2 运行时参数模型

当前报表运行时参数模型由两部分组成：

- `parameters`
  - 模板级显式参数输入
- `interactions`
  - 预览联动产生的上下文参数

这两类参数统一写入：

- 预览请求
- 导出请求
- 调度请求
- 快照记录

### 8.3 版本治理

当前模板版本治理已包含：

- `draftVersion`
- `publishedVersion`
- `effectiveVersion`
- `state`

并配套：

- 草稿保存
- 发布
- 最小结构校验
- 乐观锁冲突控制
- 调度版本绑定

## 9. ETL 子系统设计

### 9.1 主题模型

当前 ETL 已支持：

- `cdm_patient`
- `cdm_encounter`
- `cdm_lab`
- `cdm_lab_result`
- `cdm_medication_order`

### 9.2 绑定模型

ETL 当前采用“语义字段绑定 + 兼容旧字段”的双轨策略：

- 新请求优先使用 `fieldBindings`
- 老记录继续兼容 `idField/nameField/...`
- 后端最终统一存入 `field_bindings_json`

这种设计降低了新增主题时的前后端硬编码成本。

### 9.3 执行策略

ETL 执行时：

- 从外部数据源读取数据
- 生成原始记录 JSON
- 落地 ODS
- 按主题规则写入对应 CDM 表
- 记录运行状态和抽取数量
- 增量任务更新 checkpoint

## 10. 开放 API 子系统设计

### 10.1 接口范围

当前开放接口包括：

- `/open-api/v1/patients`
- `/open-api/v1/encounters`
- `/open-api/v1/labs`
- `/open-api/v1/medications`
- `/open-api/v1/reports`

### 10.2 查询策略

开放 API 采用：

- 动态 SQL 条件拼接
- 统一的日期范围参数风格
- 脱敏字段后处理
- 返回条数日志记录

### 10.3 限流策略

当前限流支持：

- Redis 令牌桶优先
- Redis 不可用时回退到进程内限流

这使系统在本地开发和容器演示环境中都具备可运行性。

## 11. 部署架构设计

### 11.1 开发版

开发版特点：

- 前端和后端都对宿主机开放端口
- 适合接口调试和本地联调
- 可直接访问 Swagger、后端健康检查

### 11.2 生产版

生产版特点：

- 仅开放 Nginx `18081/18443`
- 后端、TiDB、Redis 只在容器网络内部通信
- 开启 HTTPS 与 HSTS
- 使用更严格的生产参数校验

### 11.3 数据初始化

生产版初始化分两步：

1. `tidb-init`
   - 创建数据库
   - 创建应用用户
   - 授权
2. Spring Boot + Flyway
   - 执行结构迁移和种子数据初始化

## 12. 可观测性与运维设计

当前系统已具备基础可观测能力：

- `actuator/health`
- 请求 ID 透传
- 审计日志
- 开放 API 访问日志
- Quartz 调度恢复
- 容器日志

当前建议结合以下入口排障：

- `docker compose logs backend`
- `docker compose logs frontend`
- `flyway_schema_history`
- `sys_audit_log`
- `api_access_log`

## 13. 当前约束与后续演进

### 13.1 当前约束

- 后端仍以模块化单体为主，未拆分微服务
- 数据访问以 `JdbcTemplate` 为主，复杂领域模型尚未抽象为独立领域层
- 报表设计器已具备结构化能力，但离完整 BI 级拖拽仍有差距
- ETL 主题和转换规则仍偏 MVP，复杂异构源适配需继续扩展

### 13.2 后续建议

- 补齐报表发布前兼容性检查
- 增强模板变更摘要与回滚能力
- 扩展更多 CDM 主题和更复杂转换规则
- 提高覆盖率门禁并固化 Required checks
- 引入更完整的监控、告警、备份与 Secret 托管

## 14. 结论

当前 `MedicalDataCenter` 已形成“前端控制台 + 后端模块化单体 + TiDB/Redis + Nginx + Docker Compose”的完整 MVP 架构，核心主链路已经闭环：

- 身份认证闭环
- 数据源接入闭环
- ETL 标准化闭环
- 报表设计与调度闭环
- 开放 API 调用闭环
- 部署与安全治理闭环

后续演进重点不再是“从无到有”，而是围绕兼容性、规模化、可观测性和生产治理能力继续增强。
