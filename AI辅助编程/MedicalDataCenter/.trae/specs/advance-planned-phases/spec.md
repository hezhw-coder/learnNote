# MedicalDataCenter 后续阶段连续推进 Spec

## Why
当前项目已完成 MVP 一期主干建设与收口，但根据原始计划文档与最新项目进度说明，仍存在若干已明确排在后续优先级中的计划内增强项。需要以“按阶段连续推进”的方式，围绕既定路线继续完善项目，并在一个阶段完成后自动进入下一个阶段，避免反复停顿确认。

## What Changes
- 按既定优先级定义后续连续推进阶段，覆盖多主题 ETL、报表设计器增强、开放 API 生产化增强、验收级测试与交付材料增强
- 每个阶段仅实现原计划范围内最小可验收闭环，不超范围扩展
- 阶段完成后自动推进下一阶段，直到当前规格范围内的阶段任务全部完成
- 每个阶段均同步更新测试、文档、进度台账与验证记录
- 建立跨阶段的可追溯变更与验收清单

## Impact
- Affected specs: ETL 与标准化、报表设计器、开放 API、测试与交付、文档治理
- Affected code: `backend/src/**`、`frontend/src/**`、`backend/src/main/resources/db/migration/**`、`tests/**`、`docs/**`

## ADDED Requirements
### Requirement: 阶段化连续推进
系统 SHALL 将后续计划内工作拆分为连续阶段，并在一个阶段完成后自动进入下一阶段执行，无需逐阶段等待额外确认。

#### Scenario: 阶段完成后自动推进
- **WHEN** 当前阶段任务、验证与文档更新全部完成
- **THEN** 实现流程必须自动开始下一个已定义阶段
- **THEN** 不得再次就“是否继续下一阶段”发起确认

### Requirement: 多主题 ETL 持续扩展
系统 SHALL 在现有 `cdm_patient`、`cdm_lab_result` 基础上，继续向原始规划中的医疗主题模型扩展，优先补齐至少一个新的标准化主题闭环。

#### Scenario: 新增一个医疗主题
- **WHEN** 进入 ETL 扩展阶段
- **THEN** 系统必须为新增主题补齐 ODS、CDM、元数据、样例预览与最小验证链路
- **THEN** 新主题应可被报表设计器或开放 API 复用

### Requirement: 报表设计器持续增强
系统 SHALL 在现有最小闭环基础上，继续增强低代码配置能力，但仍保持在原计划的 MVP 拖拽报表设计器范围内。

#### Scenario: 增强报表设计交互
- **WHEN** 进入报表设计器增强阶段
- **THEN** 系统必须补齐当前影响使用体验的核心能力，例如更清晰的布局交互、绑定配置、组件编排或任务联动
- **THEN** 增强后的设计器仍需保证预览、导出与调度配置的一致性

### Requirement: 开放 API 持续增强
系统 SHALL 继续完善开放 API 的计划内能力，包括更多真实主题、筛选控制、脱敏与访问控制增强，但不超出当前技术路线。

#### Scenario: 扩展开放主题与控制能力
- **WHEN** 进入开放 API 增强阶段
- **THEN** 系统必须在现有真实接口基础上继续补齐计划内主题或关键过滤能力
- **THEN** 应保持与 OAuth2/JWT、scope、日志、限流机制的一致性

### Requirement: 验收级测试与材料增强
系统 SHALL 在最小回归基础上继续增强为更接近验收级的测试与交付材料体系。

#### Scenario: 完成一个增强阶段
- **WHEN** 任一阶段开发完成
- **THEN** 必须同步补充该阶段对应的测试、回归步骤、文档说明与进度台账
- **THEN** 必须形成可追溯的阶段结果与验证结论

## MODIFIED Requirements
### Requirement: 计划推进方式
系统 SHALL 从“按单个规格完成一个收口任务”升级为“在当前规格范围内按阶段连续推进多个计划内增强主题”，但仍保持每阶段均有明确边界与验收点。

#### Scenario: 组织后续工作
- **WHEN** 团队进入后续阶段开发
- **THEN** 必须按既定阶段顺序推进
- **THEN** 每个阶段都应定义独立的任务、验证点与文档更新范围

### Requirement: 文档与进度台账
系统 SHALL 在每个阶段完成后更新 `docs/项目进度说明.md`，使其能够清晰区分“已完成阶段”“当前进行阶段”和“后续候选阶段”。

#### Scenario: 阶段交付完成
- **WHEN** 一个阶段的代码与验证完成
- **THEN** 进度台账必须更新该阶段状态与剩余工作
- **THEN** 相关交付文档必须反映当前真实实现

## REMOVED Requirements
### Requirement: 阶段间显式停顿确认
**Reason**: 用户已明确要求“开发完一个阶段自动继续下一个阶段，不用询问”。
**Migration**: 在当前规格覆盖的阶段链路中，默认采用自动连续推进；仅当出现范围冲突、重大阻断或需要用户业务决策时才中断。
