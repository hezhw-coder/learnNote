# MedicalDataCenter MVP 对齐推进 Spec

## Why
当前项目已经形成可运行的 MVP 演示版，但与原始规划文档中的功能范围、技术选型和交付标准仍存在差距。需要在不扩大范围的前提下，系统性识别偏差、补齐核心短板、修复存量问题、同步进度台账，并建立可追溯的变更与验证闭环。

## What Changes
- 梳理当前实现与原始 MVP 计划之间的能力偏差，并形成可执行的收敛范围
- 按原定 MVP 范围补齐未完成的核心模块能力，不新增超出规划的新业务域
- 修复影响 TiDB/Docker 运行、联调、验收和功能闭环的现存问题
- 统一代码、接口、联调脚本、部署文档与进度台账之间的不一致项
- 建立面向迭代的可追溯变更记录、任务清单和验证清单

## Impact
- Affected specs: 数据源管理、ETL 与标准化、报表设计器、开放 API、系统管理、测试与交付、文档治理
- Affected code: `frontend/src/**`、`backend/src/**`、`backend/src/main/resources/db/migration/**`、`docker/**`、`tests/**`、`docs/**`

## ADDED Requirements
### Requirement: MVP 偏差对齐机制
系统 SHALL 基于原始 MVP 规划文档与当前项目进度说明，输出明确的偏差清单，并将后续迭代严格限定在原定 MVP 功能范围、技术选型和交付标准之内。

#### Scenario: 识别规划偏差
- **WHEN** 团队启动一次新的 MVP 推进迭代
- **THEN** 必须先对照原始规划与当前进度，识别已完成项、未完成项、偏差项和阻塞项
- **THEN** 偏差项必须被映射到明确的任务、验证方式和文档更新动作

### Requirement: 关键能力补齐闭环
系统 SHALL 优先补齐影响 MVP 验收的核心缺口，包括 ETL 标准化主题扩展、报表设计器关键能力、开放 API 真值接口、系统管理写能力、测试验证与交付收口。

#### Scenario: 补齐未完成的核心模块
- **WHEN** 某模块已被识别为 MVP 核心缺口
- **THEN** 必须先补足该模块最小可验收闭环
- **THEN** 实现不得偏离原始技术路线，例如前端继续采用 `Vite + Vue + TypeScript`，后端继续采用 `Spring Boot + Maven`，主库继续采用 `TiDB`

### Requirement: 运行问题优先修复
系统 SHALL 先修复影响主链路稳定运行、Docker 部署、TiDB 兼容、接口契约一致性和联调验证的现存问题，再推进功能扩展。

#### Scenario: 存在阻断性交付问题
- **WHEN** 发现 SQL 方言不兼容、接口文档失真、联调脚本不可用、部署说明与实际不符等问题
- **THEN** 这些问题必须优先进入当前迭代范围
- **THEN** 修复后必须同步更新相关文档和验证记录

### Requirement: 进度台账与变更留痕
系统 SHALL 为每一次面向 MVP 的推进迭代维护可追溯的变更记录、进度状态和验证结果。

#### Scenario: 完成一次迭代交付
- **WHEN** 任一功能、修复或文档更新完成
- **THEN** 必须同步更新任务状态、进度说明、相关说明文档和验证清单
- **THEN** 必须能够追溯该变更对应的需求来源、实现范围和验证结果

### Requirement: 验收导向验证
系统 SHALL 围绕原始 MVP 计划中的验收目标建立验证闭环，覆盖单元测试、集成测试、联调验证、部署验证和文档检查。

#### Scenario: 准备进入阶段性交付
- **WHEN** 团队声明某一阶段功能已完成
- **THEN** 必须验证关键主链路，包括登录、数据源管理、ETL、报表预览与导出、开放 API 鉴权与访问、Docker 部署
- **THEN** 验证结果必须能够回写到文档或清单中

## MODIFIED Requirements
### Requirement: ETL 与标准化模块
系统 SHALL 在现有 `cdm_patient` 示例能力基础上，继续向原始 MVP 计划定义的医疗主题标准模型收敛，优先补足 `患者、就诊、科室、医生、医嘱、检验、检查、药品` 中尚未实现的最小闭环能力。

#### Scenario: 扩展标准化主题
- **WHEN** 系统执行一项新的标准化主题建设
- **THEN** 必须覆盖数据接入、ODS 入仓、CDM 转换、元数据暴露和样例预览
- **THEN** 需要兼顾 TiDB 方言兼容与后续报表、开放 API 的复用

### Requirement: 报表设计器
系统 SHALL 从当前轻量版 JSON Schema 设计器继续演进到原始 MVP 所要求的低代码拖拽版报表设计器的最小可验收形态，但不扩展到自由像素级复杂编辑器。

#### Scenario: 对齐报表设计能力
- **WHEN** 用户在报表设计器中配置组件
- **THEN** 系统至少应支持组件面板、布局编辑、属性配置、数据绑定、预览与导出一致性
- **THEN** 与定时任务、报表快照和站内通知的链路必须可验证

### Requirement: 开放 API
系统 SHALL 将当前开放 API 的演示能力收敛到原始 MVP 规划的真实接口能力，重点补足 OAuth2/JWT 交互一致性、真实数据返回、限流能力和访问日志。

#### Scenario: 第三方调用开放接口
- **WHEN** 第三方应用申请令牌并访问开放接口
- **THEN** 系统应返回真实可用的数据结果而非长期占位数据
- **THEN** 需要记录访问日志并执行符合规划的限流控制

### Requirement: 系统管理
系统 SHALL 在现有查询展示能力基础上补齐最小可运营后台能力，包括用户、角色、权限或关键系统配置的写操作闭环。

#### Scenario: 平台管理员维护基础配置
- **WHEN** 管理员执行用户、角色或系统配置维护动作
- **THEN** 系统应提供符合权限控制的写操作能力
- **THEN** 关键操作应纳入审计记录

### Requirement: 文档与交付物
系统 SHALL 保持部署文档、使用手册、接口说明、联调脚本和项目进度说明与实际代码实现同步。

#### Scenario: 代码能力发生变化
- **WHEN** 接口字段、运行方式、验收状态或模块能力发生变化
- **THEN** 相关文档必须在同一迭代内完成更新
- **THEN** 文档不得继续保留已知过时内容

## REMOVED Requirements
### Requirement: 隐式推进方式
**Reason**: 当前项目已进入多模块并行推进阶段，仅靠零散对话难以保证范围控制、偏差追踪和验证闭环。
**Migration**: 后续所有针对 MVP 的持续推进工作，都应通过规格、任务、清单和进度记录来驱动与追踪。
