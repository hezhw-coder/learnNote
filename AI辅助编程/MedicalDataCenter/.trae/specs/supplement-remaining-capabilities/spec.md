# MedicalDataCenter 剩余功能补全 Spec

## Why
基于既有 `align-mvp-delivery`、`complete-mvp-hardening`、`advance-planned-phases` 三组规格与 `medical-data-center-mvp-plan.md`，当前项目已完成 MVP 主干与若干计划内增强，但仍存在一批“已明确属于后续范围、尚未形成完整闭环”的功能模块。需要统一梳理当前已实现范围、冻结剩余功能清单，并为每个未完成模块补足技术实现方案、接口契约、交互逻辑、异常处理与验证标准，保证后续开发和验收有完整、一致、可追溯的规格基线。

## What Changes
- 梳理当前已实现范围，明确哪些能力已达到“可运行/可验收/仅增强项”的状态
- 识别剩余未完成功能，覆盖 `ETL/CDM`、报表设计器、开放 API、系统/安全治理、测试与交付文档
- 为每个剩余功能补充技术实现方案，包括模块职责、数据流、关键接口、前后端交互、依赖边界
- 为每个剩余功能补充异常处理机制、边界条件覆盖要求与回退策略
- 形成一套完整的功能验证 checklist，用于后续实现完成后的逐项验收
- 同步在 `/spec` 路径下新增一组规格文档，作为后续剩余能力补全的统一规格入口
- 当前已实现范围基线：
  - 认证、JWT、RBAC、审计、会话续期、退出登录、基础密码策略与账号失败控制已具备最小闭环
  - 数据源管理已形成较完整 CRUD、连接测试、状态切换闭环
  - `ETL` 已支持患者、检验结果、用药医嘱三个主题的最小 `ODS -> CDM -> 数据集` 主链路
  - 报表设计器已支持模板保存、预览、导出、调度复用、筛选条件配置与基础组件编排
  - 开放 API 已支持患者、就诊、检验、用药医嘱、报表查询及最小 `OAuth2/JWT + scope + 限流 + 日志` 能力
  - 测试、CI、容器回归、部署文档、交付验证记录已具备最小闭环
- 统一实现基线冻结如下：
  - 工程与部署基线：`frontend + backend + docker + docs + tests` 单仓结构已落地，`TiDB + Redis + Nginx + Flyway` 主链路可运行
  - 认证与权限基线：平台账号登录、JWT、RBAC、审计、服务端会话续期、退出登录、密码策略、失败锁定与最小生产安全参数校验已落地
  - 数据接入基线：数据源管理 CRUD、连通性测试、状态切换、敏感配置加密保存、前后端联调已具备稳定闭环
  - 数据处理基线：`ETL` 已形成 `患者/检验结果/用药医嘱` 三主题的 `ODS -> CDM -> 数据集预览` 最小统一模式，增量 checkpoint 已具备基础逻辑
  - 数据消费基线：报表设计器已支持模板保存、筛选配置、预览、`PDF/Excel` 导出、调度复用统一模板解析；开放 API 已支持真实主题查询、默认脱敏、scope、限流与访问日志
  - 交付验证基线：已存在前端最小单测、后端集成测试、覆盖率输出入口、`compose-smoke` 容器回归、部署文档、使用手册、接口说明与交付验证记录
- 当前剩余功能冻结范围：
  - `ETL/CDM` 继续扩展就诊、科室、医生、检查、药品等计划内主题，并补强失败重试、调度、能力矩阵
  - 报表设计器补齐真正的拖拽布局、多组件联动、版本/发布治理
  - 开放 API 补齐更细粒度 scope、脱敏策略、更多主题筛选与契约描述
  - 系统/安全补齐字典治理、细粒度权限编排、数据权限与更明确的生产安全基线
    - 字典治理以“字典类型 + 字典项”两级模型统一承载数据源类型、报表渠道、任务状态、脱敏模板、告警级别等可配置枚举，要求支持编码唯一、名称展示、启停、排序、软删除、内置项保护、引用计数与审计留痕
    - 系统参数按 `security`、`runtime`、`integration`、`feature`、`business` 五类归档；`security` 类参数仅允许查看元数据和生效状态，不允许在 `sys_parameter` 中直接托管密钥、口令、令牌和证书正文
    - 字典与参数都必须提供明确的引用面清单，至少覆盖 `frontend/src/pages/system`、`backend/src/main/java/com/medicaldatacenter/backend/system`、开放 API scope/脱敏配置、ETL 运行状态与报表调度渠道等消费方
    - 启停策略必须区分“新建引用禁止”和“历史引用兼容”两类行为：停用后禁止新增绑定，但历史数据回显和审计查询仍可展示原值
    - 排序规则统一使用升序整数，列表回显、下拉渲染、导出顺序和开放接口元数据输出必须一致
    - 引用校验必须在删除、停用、编码变更三类写操作前执行；若存在活动引用，系统只允许转为停用或创建替代项，不允许无提示硬删除
  - 系统/安全剩余能力的实现边界冻结如下：
    - 后端以 `SystemModule` 及其后续拆分子模块承载字典、参数、角色、权限、审计与安全基线校验；前端以 `SystemPage.vue` 及菜单守卫承载可见性、禁用态和拒绝提示；数据库迁移负责治理类元数据表、引用索引和内置种子数据
    - 菜单权限决定路由与导航是否可见，动作权限决定按钮、提交入口和写接口是否可用，数据范围权限决定列表/详情查询谓词，字段权限决定字段是否明文、脱敏或完全隐藏；四者必须串行判定、默认拒绝
    - 前端仅可根据权限结果做展示降级，后端必须作为最终裁决者；任一接口不能因前端已隐藏按钮而省略服务端鉴权
    - 数据范围与字段权限既适用于管理端页面，也适用于开放 API 与导出文件；脱敏结果必须在页面预览、接口响应、导出文件、审计快照之间保持一致
    - 生产安全基线以 `application-prod.yml`、`docker-compose.prod.yml`、`default.prod.conf` 为主入口，要求 `JWT/AES` 活跃密钥、历史兼容密钥、HTTPS 入口、HSTS、受信任来源、审计上下文字段和 Secret 挂载路径全部可校验
    - 密钥轮换必须采用“双版本兼容窗口”策略：新令牌/新密文使用 active key，历史令牌/历史密文在配置的 previous keys 窗口内仍可验证或解密，超窗后才允许彻底移除旧 key
  - 测试与交付补齐更深交互测试、更高覆盖率门禁、验收制品和模块级操作说明
-  - 测试与交付补齐“功能域 -> 自动化层级 -> 人工验收 -> 文档责任人”的映射关系，并冻结失败制品与回归入口
- 剩余能力冻结清单如下：
  - `P0 / ETL-CDM`：扩展 `encounter / department / practitioner / exam / drug` 等计划内主题，统一补齐 `ODS/CDM` 映射、元数据、样例预览、下游复用、迁移脚本
  - `P0 / 报表设计器`：补齐真正的拖拽布局、栅格占位、组件排序、布局 JSON 约束，消除当前“轻量编排但非完整拖拽”的能力差距
  - `P1 / 开放 API`：扩展更多主题与筛选参数，细化 scope、字段脱敏、错误码与契约文档同步机制
  - `P1 / 系统与安全治理`：补齐字典治理、菜单/动作/数据/字段权限协同、`prod` 安全基线、密钥轮换与敏感参数托管要求
  - `P2 / 测试与交付`：补齐更深前端交互测试、后端模块测试、容器回归制品、覆盖率门禁抬升与模块级操作手册
- 优先级与依赖口径冻结如下：
  - `P0` 先处理“直接决定后续模块是否有统一数据与交互基线”的能力，即 `ETL/CDM` 和报表设计器
  - `P1` 在 `P0` 稳定后处理“对外契约与治理增强”的能力，即开放 API、系统治理与安全增强
  - `P2` 以“为全部剩余功能提供验收和交付闭环”为目标，依赖前述模块规格先明确
  - 报表设计器依赖数据集元数据、样例预览和模板可复用数据结构，因此依赖 `ETL/CDM` 基线扩展结果
  - 开放 API 依赖主题标准化、字段口径、脱敏边界和权限模型，因此依赖 `ETL/CDM` 与系统/安全治理口径
  - 测试与交付依赖所有剩余功能域的规格冻结结果，因此在依赖链上位于最后统一收口
- `ETL/CDM` 剩余能力章节冻结如下：
  - 主题扩展顺序按 `encounter -> department -> practitioner -> exam -> drug` 推进；其中 `encounter` 作为后续关系主轴，`department` 与 `practitioner` 为维表依赖主题，`exam` 与 `drug` 为消费型事实主题
  - 每个新增主题的最小闭环标准必须同时满足：存在 `ODS` 抽取配置、存在 `CDM` 标准表与字段映射、存在元数据定义、存在至少一份样例预览数据、存在至少一个下游复用入口、存在数据库迁移脚本与回滚边界说明
  - 主题间依赖必须遵循“先维表、后事实；先核心关联主轴、后扩展消费主题”的顺序；未完成前置依赖时，后续主题不得标记为可发布
  - `ODS` 边界负责保留源系统原始命名、主键与增量游标；`CDM` 边界负责统一编码、标准枚举、关联键、脱敏口径与面向消费端的字段别名
  - 元数据必须至少包含主题编码、中文名称、来源表/视图、默认增量字段、主键策略、刷新方式、字段级类型/脱敏/字典映射说明、下游复用清单
  - 样例预览必须支持按主题返回固定条数标准化样例，并同时暴露原始值、标准化值、映射状态、异常标记四类信息，供数据集预览、报表绑定与接口联调复用
  - 下游复用边界冻结为：`encounter` 至少复用到开放 API 或数据集，`department` 与 `practitioner` 至少复用到筛选字典或维度联想，`exam` 与 `drug` 至少复用到报表设计器或开放 API 查询
  - 数据库迁移必须按主题拆分 `Flyway` 脚本，覆盖 `ODS` 表、`CDM` 表、索引、唯一键、元数据初始化与回填脚本；禁止在同一迁移中混入两个主题的结构变更
  - 调度执行约束冻结为：同一数据源同一主题在同一时间仅允许一个运行实例；支持手动触发、计划调度、失败重跑三类入口，且均复用统一执行记录模型
  - 失败重试策略冻结为：连接类与暂时性写入失败可自动重试，字段映射缺失、元数据缺失、必填主键缺失、目标结构不兼容必须直接失败并等待人工修复；自动重试次数、退避间隔与最终状态必须可审计
  - 并发控制必须至少覆盖数据源级互斥、主题级互斥、全局执行槽位上限；当资源不足或存在运行中实例时，新任务应进入排队或返回显式拒绝原因
  - 能力矩阵必须按数据源类型声明是否支持全量/增量、时间戳游标、主键游标、分页抽取、元数据探测、样例预览、失败重跑；前端仅可展示被矩阵允许的配置项
  - 告警当前允许以占位方式落地，但规格必须预留任务失败、重试耗尽、长时间运行、样例预览异常、迁移缺失五类告警事件及其消息字段
  - ETL 异常处理必须覆盖连接失败、认证失败、源表不存在、字段缺失、类型转换失败、字典映射失败、脏数据过滤、重复主键冲突、增量游标回退、任务取消、超时中断与目标写入失败
  - ETL 边界条件验证必须覆盖空表抽取、单批次超大数据量、分页越界、重复调度触发、历史游标损坏、主题禁用后触发、迁移未执行即运行、下游引用尚未准备完毕、部分成功批次重放幂等性

## Impact
- Affected specs: `ETL 与标准化`、`报表设计器`、`开放 API`、`系统管理`、`安全治理`、`测试与交付`
- Affected code: `backend/src/**`、`frontend/src/**`、`backend/src/main/resources/db/migration/**`、`tests/**`、`docs/**`、`.github/workflows/**`

## ADDED Requirements
### Requirement: 剩余功能范围盘点基线
系统 SHALL 在规格层面提供“当前已实现范围”和“剩余未完成能力”两张清单，并为后续实现提供统一边界。

#### Scenario: 评估当前项目状态
- **WHEN** 团队依据当前代码、既有规格与项目计划进行盘点
- **THEN** 规格必须明确列出已完成主链路、已完成但仍可增强的能力、以及未完成的剩余模块
- **THEN** 每个剩余模块必须标注其所属业务域、优先级与与现有模块的集成关系

#### Scenario: 冻结统一实现基线
- **WHEN** 团队将当前项目状态作为后续剩余能力补全的起点
- **THEN** 规格必须按“工程部署、认证权限、数据接入、数据处理、数据消费、交付验证”六个维度给出统一实现基线
- **THEN** 任一后续任务不得回退或重定义上述基线，只能在其上补齐明确列出的剩余能力

#### Scenario: 生成剩余能力优先级与依赖矩阵
- **WHEN** 团队拆解剩余能力的实现顺序
- **THEN** 规格必须为每个剩余能力域标注 `P0/P1/P2` 优先级、前置依赖、受影响模块和推荐集成位置
- **THEN** 测试、交付与文档类事项必须依赖功能域规格先冻结，不得脱离功能规格独立提前收口

### Requirement: ETL/CDM 剩余能力补全方案
系统 SHALL 为剩余医疗主题扩展与运行治理补齐详细技术方案，覆盖主题扩展、任务调度、失败处理与能力矩阵。

#### Scenario: 扩展新的标准化医疗主题
- **WHEN** 团队为计划内新增主题（如就诊、科室、医生、检查、药品）实施补全
- **THEN** 规格必须定义新增主题的 `ODS` 来源、`CDM` 目标表、字段映射规则、元数据、样例预览与复用位置
- **THEN** 新主题应可被数据集、报表设计器或开放 API 至少一个下游模块复用
- **THEN** 新主题必须按 `encounter -> department -> practitioner -> exam -> drug` 的顺序扩展，并满足“抽取、标准化、元数据、预览、复用、迁移”六项最小闭环标准后方可进入可验收状态
- **THEN** 若后续主题依赖前置维表或主轴主题，规格必须明确阻塞关系与不可跳过的发布前提

#### Scenario: ETL 执行失败
- **WHEN** 抽取任务执行过程中发生连接失败、字段映射缺失、增量游标异常、目标表写入失败或任务超时
- **THEN** 系统应记录明确失败阶段、失败原因、重试次数与可重放上下文
- **THEN** 规格应定义失败重试策略、并发限制、人工重跑入口与告警占位
- **THEN** 自动重试仅适用于连接抖动、暂时性写入失败等瞬时异常，映射缺失、主键缺失、迁移未执行、结构不兼容等配置类问题必须直接失败并要求人工介入
- **THEN** 同一数据源同一主题不得并发执行；若任务因互斥限制未启动，系统必须记录排队或拒绝原因

#### Scenario: 数据源能力差异
- **WHEN** 不同数据源不支持相同增量策略、分页方式或元数据探测能力
- **THEN** 系统应通过能力矩阵约束前端可选项
- **THEN** 不支持的策略不得在 UI 中默认暴露为可执行配置
- **THEN** 能力矩阵至少应声明全量/增量、时间戳游标、主键游标、分页抽取、元数据探测、样例预览与失败重跑七类能力
- **THEN** 基于不支持能力生成的历史配置在保存、调度或运行前必须被阻断并返回明确原因

#### Scenario: 校验 ETL 结构边界
- **WHEN** 团队为新增主题补充 `ODS`、`CDM`、元数据与迁移脚本
- **THEN** 规格必须明确 `ODS` 负责原始数据留存与增量游标，`CDM` 负责标准编码、统一字段口径、关联键和消费别名，不得混用职责
- **THEN** 每个主题必须独立维护迁移脚本、索引与初始化数据边界，禁止将多个主题的结构调整合并为一个不可拆分变更

#### Scenario: 验证 ETL 异常与边界条件
- **WHEN** 团队编写新增主题的实现与验收用例
- **THEN** 规格必须覆盖连接失败、源表不存在、字段缺失、类型转换失败、脏数据过滤、重复主键冲突、游标损坏、迁移缺失、任务取消与超时中断等异常场景
- **THEN** 规格必须覆盖空数据、超大批次、分页越界、重复触发、主题禁用后误触发、部分成功后重放幂等与下游依赖未就绪等边界条件

### Requirement: 报表设计器剩余能力补全方案
系统 SHALL 为低代码报表设计器补齐拖拽布局、联动交互、模板版本与发布治理的规格定义。

#### Scenario: 定义拖拽布局与模板结构约束
- **WHEN** 团队为报表设计器实现真正的拖拽布局与栅格编排能力
- **THEN** 模板 `designJson` 必须至少包含 `schemaVersion`、`datasetCode`、`layout`、`components`、`filters`、`interactions`、`versioning` 七个一级节点
- **THEN** `layout` 必须显式记录 `gridColumns`、`rowHeight`、`gap`、`canvasWidthMode`，其中默认栅格按 `24` 列实现，单组件 `w` 取值范围为 `1-24`
- **THEN** 每个组件必须保存稳定的 `componentId`、`type`、`title`、`grid`、`binding`、`style`、`sortOrder`、`visibility` 信息，且复制组件时必须生成新的 `componentId`
- **THEN** `grid` 必须采用 `x/y/w/h` 四元组表达占位，保存前必须执行“无越界、无负值、无重叠、无遮挡主键冲突”校验
- **THEN** 组件排序必须同时支持画布拖拽排序和显式“上移/下移/置顶/置底”命令，并以 `y -> x -> sortOrder -> createdAt` 作为稳定回显顺序
- **THEN** 拖拽过程中栅格占位必须提供可视化落点，释放鼠标后若目标区域非法，系统必须回退到上一个合法布局，不得保存半有效状态

#### Scenario: 维护复杂筛选与绑定扩展
- **WHEN** 用户为模板配置复杂筛选、组件绑定和参数透传
- **THEN** 模板必须支持 `templateFilters`、`componentFilters`、`runtimeFilters` 三层过滤结构，并明确优先级为 `runtimeFilters > componentFilters > templateFilters`
- **THEN** 复杂筛选必须支持分组表达，至少支持 `AND/OR` 组合、最多 `3` 层条件分组，以及 `=`、`!=`、`>`、`>=`、`<`、`<=`、`IN`、`BETWEEN`、`LIKE`、`IS_NULL`、`IS_NOT_NULL` 操作符
- **THEN** 组件绑定必须区分 `dimensions`、`measures`、`sorts`、`limit`、`formatters`、`emptyStateText`，并要求每个绑定字段都能在数据集元数据中被解析
- **THEN** 字段绑定扩展必须允许为同一组件定义显示别名、格式化规则、默认排序和聚合函数，但不得绕过数据集字段权限与脱敏策略
- **THEN** 若模板引用的字段在数据集元数据中不存在、被停用或类型不兼容，设计器必须阻止发布并给出定位到字段级别的校验信息

#### Scenario: 定义多组件联动与跨通道一致性
- **WHEN** 用户在图表、指标卡、表格之间配置联动关系
- **THEN** 每条联动规则必须至少记录 `interactionId`、`sourceComponentId`、`targetComponentIds`、`triggerField`、`targetField`、`operator`、`valueMode`、`emptyBehavior`、`cascadeMode`
- **THEN** 系统必须支持点击联动、选择器联动和全局筛选栏联动三类触发方式，并统一通过同一套模板解析器生成最终 `resolvedTemplate`
- **THEN** 联动清空时必须支持 `clearTargets`、`restoreDefaultFilters`、`keepManualFilters` 三种策略，避免组件残留脏筛选状态
- **THEN** 若联动配置形成循环依赖、跨数据集引用、目标字段不存在或目标组件被删除，保存和发布都必须失败，并返回明确的规则编号与组件定位信息
- **THEN** 预览、`PDF`、`Excel` 导出和调度执行必须复用同一套 `resolvedTemplate + parameterSnapshot + appliedFilters` 结果，不允许各通道自行补默认值
- **THEN** 调度执行生成的快照必须额外持久化 `triggerSource`、`resolvedTemplateVersion`、`filterDigest`、`bindingDigest` 与运行时参数，以便回放和审计

#### Scenario: 管理模板版本、发布流程与回滚策略
- **WHEN** 用户保存草稿、提交发布、回滚历史模板或处理并发编辑
- **THEN** 报表模板必须区分 `draftVersion`、`publishedVersion`、`effectiveVersion`、`archivedVersion` 四类状态，并保证任意时刻仅允许一个 `effectiveVersion`
- **THEN** 保存草稿必须基于乐观锁版本号执行，若前端提交的 `baseVersion` 落后于服务端最新草稿版本，接口必须返回 `409` 冲突并要求用户重新合并
- **THEN** 发布前必须完成布局校验、字段绑定校验、联动校验、最小预览成功校验和权限校验，任一失败都不得进入已发布状态
- **THEN** 发布成功后，已发布版本必须视为只读快照；后续修改只能基于其派生新草稿，不得原地覆盖历史版本
- **THEN** 回滚操作必须以“选择历史版本 -> 生成新草稿 -> 重新校验 -> 再次发布”的方式执行，不允许直接把历史版本硬切换为生效版本
- **THEN** 调度任务、导出记录和外部引用必须保存 `templateId + effectiveVersion`；若业务要求自动跟随最新发布版本，必须在任务级别显式声明 `followLatestPublished=true`
- **THEN** 新版本删除字段、缩减组件或调整联动时，系统必须对引用中的调度任务执行兼容性检查；不兼容时仅允许保存草稿，不允许直接发布覆盖

#### Scenario: 处理设计器异常与边界条件
- **WHEN** 报表设计器出现参数非法、布局冲突、空数据、重复提交、版本兼容或下游依赖缺失等异常
- **THEN** 系统必须把异常分类为 `VALIDATION_ERROR`、`STATE_CONFLICT`、`DEPENDENCY_MISSING`、`RENDER_FAILED`、`EXPORT_FAILED`、`SCHEDULE_BLOCKED` 六类，并返回统一错误结构
- **THEN** 空数据预览不得视为失败，必须保留组件骨架、标题、筛选摘要和“无数据”占位说明，导出结果也必须包含相同的参数摘要
- **THEN** 同一模板的重复保存、重复发布、重复回滚请求必须具备幂等保护，至少基于 `templateId + clientRequestId` 或版本号实现去重
- **THEN** 当调度运行时引用的模板版本已归档、数据集被禁用、必填参数缺失或导出通道不可用时，任务必须阻断执行并记录明确的阻断原因，不得静默降级到其他版本
- **THEN** 历史模板升级到新 `schemaVersion` 时必须提供向后兼容转换器；若无法自动转换，系统必须在设计器中提示人工迁移，且禁止直接发布
- **THEN** 验收清单必须至少覆盖拖拽越界、重叠占位、复制后 `componentId` 唯一性、复杂筛选优先级、联动清空策略、发布冲突、历史回滚、空数据导出与调度兼容性九类边界场景

#### Scenario: 设计器拖拽编排
- **WHEN** 用户在报表设计器中调整组件布局
- **THEN** 系统应支持明确的拖拽、占位、排序与栅格对齐交互
- **THEN** 规格必须定义拖拽后的模板 JSON 结构、保存约束与回显规则

#### Scenario: 多组件联动筛选
- **WHEN** 用户配置图表、指标卡、表格之间的联动条件
- **THEN** 系统应定义联动源组件、目标组件、触发字段、过滤条件与清空行为
- **THEN** 预览、导出与调度快照必须共享同一套联动后的模板解析结果

#### Scenario: 模板版本与发布
- **WHEN** 用户保存草稿、发布模板或回滚历史版本
- **THEN** 系统应区分草稿版本、已发布版本与当前生效版本
- **THEN** 规格必须定义版本冲突、发布校验失败、引用中的调度模板如何保持兼容

### Requirement: 开放 API 剩余能力补全方案
系统 SHALL 为开放 API 的剩余计划内能力补齐主题扩展、契约治理、scope 细化与脱敏策略。

#### Scenario: 扩展开放主题与筛选
- **WHEN** 新增开放主题或补齐现有主题缺失筛选能力
- **THEN** 现有 `patients`、`encounters`、`labs`、`medications`、`reports` 主题以及后续新增主题都必须采用 `/open-api/v1/{topic}` 的复数命名路径，且不得混用单数、下划线或版本前缀外置写法
- **THEN** 每个主题都必须声明“精确筛选字段、关键字筛选字段、时间区间字段、分页参数、排序白名单、默认排序字段、空结果返回结构、错误码”，并同步到 `docs/API接口说明.md`
- **THEN** 分页契约统一使用 `pageNum`、`pageSize`、`sortBy`、`sortOrder`；其中 `pageNum` 默认 `1`、`pageSize` 默认 `20`、最大 `100`，`sortOrder` 仅允许 `asc/desc`
- **THEN** 列表类主题必须返回“数据列表 + 分页元信息”的统一结构；若为兼容既有数组响应而保留过渡模式，文档必须显式标注兼容期、升级目标版本和调用方迁移方式
- **THEN** 排序仅允许命中当前主题声明过的白名单字段；未声明字段、跨主题字段或敏感字段不得作为 `sortBy`
- **THEN** 空结果必须返回 `code=0`、空集合和合法分页信息，不得以 `404` 代替“查询结果为空”
- **THEN** 查询参数非法、排序字段非法、分页越界、时间区间反转等契约错误统一返回 `400`；主题不存在或路径错误返回 `404`
- **THEN** 新接口必须与现有 `OAuth2/JWT`、scope、访问日志、限流策略保持一致，且默认接入 `requestId` 透传与回显

#### Scenario: 定义新增主题的契约模板
- **WHEN** 团队继续扩展 `department`、`practitioner`、`exam`、`drug` 等计划内开放主题
- **THEN** 规格必须先给出主题与 `CDM`/标准化实体的映射关系，再定义路径、返回字段、筛选条件、排序规则、默认脱敏范围与最小测试样例
- **THEN** 同一业务概念若已存在于报表或数据集模块，其字段命名、枚举口径和时间字段语义必须保持一致，不得在开放 API 中重新定义另一套别名
- **THEN** 新主题上线前必须补齐 smoke 用例、Postman 示例、错误码说明和调用示例，避免仅有代码入口而缺少外部契约

#### Scenario: 细粒度 scope 与脱敏
- **WHEN** 第三方客户端以不同 scope 访问同一主题数据
- **THEN** 系统应按“令牌有效 -> 主题基础读取 scope -> 敏感筛选 scope -> 字段放宽 scope -> 字段级脱敏”顺序执行判定，前一步失败时不得继续向后放宽
- **THEN** 现有 `patients.read`、`encounters.read`、`labs.read`、`medications.read`、`reports.read` 作为主题基础读取 scope 保留；后续细粒度 scope 必须在此基础上追加，不得破坏现有客户端最小兼容性
- **THEN** 细粒度 scope 至少区分三类：主题读取类、敏感筛选类、字段放宽类；推荐命名为 `{topic}.read`、`{topic}.filter.sensitive`、`{topic}.read.full`
- **THEN** 默认可返回字段仅限主题编码、分类枚举、非直接身份识别字段和必要业务时间字段；姓名、证件号、手机号、地址、医生姓名等字段默认进入脱敏集
- **THEN** 当客户端仅具备主题读取 scope 时，脱敏字段必须按“部分掩码后返回”或“直接不返回”二选一，并在主题文档中明确每个字段的处理方式
- **THEN** 当客户端额外具备字段放宽 scope 时，仅可对明确授权字段解除脱敏；未被授权的字段仍按默认脱敏或禁止返回处理
- **THEN** 当调用方提交姓名关键字、医生关键字、证件号片段等敏感筛选条件时，必须同时具备对应敏感筛选 scope；否则统一返回 `403`，不得静默忽略条件
- **THEN** 规格必须定义“禁止返回”优先级高于“脱敏返回”，“脱敏返回”优先级高于“明文放宽返回”，避免因多 scope 并存导致敏感字段意外泄露

#### Scenario: 外部调用异常
- **WHEN** 第三方调用接口时出现 token 无效、scope 不足、参数非法、限流命中或内部处理失败
- **THEN** 系统应返回统一错误结构、可追踪 `requestId` 与明确的 HTTP 状态码，错误响应至少包含 `code`、`message`、`data=null`、`requestId`、`timestamp`
- **THEN** 未携带或携带无效 token 返回 `401`，scope 不足返回 `403`，参数非法返回 `400`，命中限流返回 `429`，内部处理失败返回 `500`
- **THEN** 访问日志 `api_access_log` 必须记录 `clientId`、`endpoint`、`scope`、`status`、`message`、`requestId`、`remoteIp`、`userAgent`、`durationMs` 与 `createdAt`
- **THEN** 失败日志 `message` 必须可区分 `invalid token`、`insufficient scope`、`invalid parameter`、`rate limited`、`internal error` 等摘要，避免仅记录通用失败文案
- **THEN** 成功访问日志必须保持 `ok rows=<命中条数>` 口径，以便与真实主题筛选结果和联调记录做一一核对
- **THEN** 限流失败、鉴权失败和参数校验失败都必须写入访问日志；若已进入平台审计域，还必须确保 `requestId` 可串联到管理端审计或网关日志
- **THEN** 任一主题新增、筛选变更、scope 变更、脱敏规则变更或错误码变更时，必须同步更新 `docs/API接口说明.md`、`docs/使用手册.md`、`docs/交付验证记录.md`、`tests/api/medical-data-center-smoke.http` 与 `tests/postman/MedicalDataCenter.postman_collection.json`

#### Scenario: 开放 API 边界条件与异常处理
- **WHEN** 调用方请求超大分页、空数据集、重复敏感筛选、未声明排序字段、跨主题字段筛选或下游依赖返回异常
- **THEN** `pageNum < 1`、`pageSize < 1`、`pageSize > 100`、`startDate > endDate`、布尔值格式错误、枚举值超范围等情况都必须视为参数非法并返回 `400`
- **THEN** 空数据集、最后一页无数据、合法但未命中任何记录的筛选条件都必须返回成功空结果，不得升级为异常或降级为非统一结构
- **THEN** 调用方重复提交相同请求时，读取型开放 API 必须保证幂等响应，不得因日志写入或限流计数之外的副作用导致结果不一致
- **THEN** 当筛选条件依赖当前客户端无权访问的敏感字段时，系统必须优先拒绝并返回 `403`，而不是改写为宽松查询导致结果集扩大
- **THEN** 当下游查询、缓存或限流组件异常时，必须返回统一错误结构并在日志中保留失败阶段摘要；若触发降级模式，也必须在文档中声明降级范围与联调影响

### Requirement: 系统管理与安全剩余能力补全方案
系统 SHALL 为字典治理、细粒度权限、数据权限与生产基线补齐规格定义，并保持与现有 RBAC 一致。

#### Scenario: 维护字典与系统配置
- **WHEN** 管理员维护字典项、参数分类或关键系统配置
- **THEN** 规格必须定义列表、编辑、启停、排序、引用校验与审计要求
- **THEN** 被业务模块引用中的字典项不得被无提示硬删除

#### Scenario: 字典项启停、排序与引用替换
- **WHEN** 管理员停用、调整排序或尝试删除已被业务引用的字典项
- **THEN** 系统应先检查活跃引用数量、引用模块、最近更新时间和替代项是否存在
- **THEN** 若存在活跃引用，系统仅允许“停用并阻止新增引用”或“迁移到替代项后删除”，不得直接物理删除
- **THEN** 列表、下拉、导出和开放元数据接口必须共享同一排序字段，不得出现展示顺序不一致

#### Scenario: 参数分类治理与敏感参数托管
- **WHEN** 管理员新增或更新系统参数
- **THEN** 参数必须声明所属分类、是否支持运行时热更新、是否允许在 `prod` 环境编辑、以及对应责任人
- **THEN** 包含 `secret/password/token/key/certificate` 语义的参数不得直接写入 `sys_parameter`，必须改为环境变量、挂载文件或 Secret 平台引用
- **THEN** `security` 类参数在管理端只能展示脱敏后的元数据、来源类型、最后轮换时间和最后操作人，不得回显明文

#### Scenario: 执行细粒度权限或数据权限判断
- **WHEN** 用户访问受限页面、按钮、数据集或开放字段
- **THEN** 系统应明确菜单权限、动作权限、数据范围权限和字段脱敏权限的判定顺序
- **THEN** 前后端都必须有一致的拒绝行为和降级显示规则

#### Scenario: 菜单、动作、数据范围与字段权限协同
- **WHEN** 同一请求同时命中菜单、动作、数据范围和字段权限约束
- **THEN** 判定顺序必须固定为“菜单可达性 -> 动作授权 -> 数据范围过滤 -> 字段明细裁剪/脱敏”
- **THEN** 若菜单无权则前端不装载路由且后端返回 `403`；若菜单有权但动作无权，则页面可见但按钮禁用且写接口返回 `403`
- **THEN** 数据范围过滤后若无可见记录，应返回空集合而不是越权错误；字段权限不足时应按规则返回脱敏值或完全移除字段

#### Scenario: 数据范围与字段权限冲突
- **WHEN** 角色授予了动作权限，但其数据范围仅限本人/本部门，且字段权限禁止查看敏感字段
- **THEN** 系统必须先按数据范围裁剪可访问记录，再对结果字段执行“隐藏优先于脱敏、脱敏优先于明文”的策略
- **THEN** 导出、打印、开放 API、审计快照不得绕过上述裁剪逻辑
- **THEN** 任一角色组合若存在互斥规则，应采用最严格结果，不允许通过叠加角色放宽禁止返回字段

#### Scenario: 启动生产安全基线
- **WHEN** 系统以 `prod` 模式部署
- **THEN** 规格必须定义必填安全参数、密钥轮换要求、HTTPS/HSTS、审计字段、敏感参数托管与启动失败条件
- **THEN** 缺失关键安全参数时应用应拒绝进入服务态

#### Scenario: 轮换 JWT 与加密密钥
- **WHEN** 运维在不停机或短停机窗口内轮换 `JWT` 签名密钥或数据加密密钥
- **THEN** 新配置必须同时声明 active key 标识和历史兼容 key 列表，并记录轮换开始时间、计划失效时间和变更单号
- **THEN** 系统必须对新签发令牌和新写入密文使用 active key，对历史数据继续允许 previous keys 验签或解密直至兼容窗口结束
- **THEN** 若 active key 缺失、格式非法或与 previous keys 冲突，应用启动校验必须失败

#### Scenario: 启用 HTTPS、HSTS 与审计追踪
- **WHEN** 生产网关或容器入口对外提供服务
- **THEN** 所有管理端、开放 API、OAuth2 入口都必须通过 `HTTPS` 暴露，并将明文 `HTTP` 统一重定向
- **THEN** `HSTS` 至少应配置 `max-age=31536000; includeSubDomains`，是否启用 `preload` 由运维评审后单独确认
- **THEN** 审计日志和 API 访问日志必须落下 `requestId`、操作者/客户端、来源 IP、User-Agent、状态码、耗时、目标资源和结果摘要

#### Scenario: 生产安全基线缺失或配置非法
- **WHEN** `prod` profile 缺失必填密钥、`issuer` 非 `https`、允许来源为空/通配、证书文件缺失或 Secret 挂载不可读
- **THEN** 应用必须在启动阶段直接失败，并输出可定位到配置项的错误信息
- **THEN** 系统不得以降级到演示默认值或临时关闭校验的方式继续提供服务

#### Scenario: 系统管理与安全模块异常和边界处理
- **WHEN** 管理员提交重复编码、空分类、非法排序值、内置项修改、并发更新冲突、敏感参数写入、越权访问或引用中的删除请求
- **THEN** 系统必须返回统一错误结构，明确错误码、对象类型、冲突字段、建议操作和 `requestId`
- **THEN** 对停用中、已停用、已引用、内置只读、待轮换和已过兼容窗口等状态应分别定义可执行动作，避免“状态不明”带来的误操作
- **THEN** 幂等场景如重复停用、重复绑定相同角色权限、重复触发同一轮换计划时，系统应返回成功或显式 no-op 结果，不得制造脏数据

### Requirement: 测试与交付剩余能力补全方案
系统 SHALL 为剩余功能补齐验收级测试、覆盖率门禁、回归制品与模块级操作说明。

#### Scenario: 执行验收回归
- **WHEN** 团队对新增剩余功能进行交付前验证
- **THEN** 系统应具备前端交互测试、后端模块测试、容器级主链路回归与文档化人工验收步骤
- **THEN** 规格必须定义测试入口、最低覆盖要求、失败制品留档与人工补验方式

#### Scenario: 建立测试分层映射矩阵
- **WHEN** 团队为 `ETL/CDM`、报表设计器、开放 API、系统/安全治理等剩余功能域补充测试交付方案
- **THEN** 每个功能点都必须映射到四类验证层级：前端交互测试、后端模块测试、`compose-smoke` 容器级主链路回归、人工验收 checklist；若某层级不适用，必须显式标注 `N/A` 和原因，不得留空
- **THEN** 前端交互测试主要覆盖页面状态切换、表单校验、权限降级、拖拽/联动交互、错误提示和空态回显；后端模块测试主要覆盖服务规则、接口契约、权限裁剪、异常路径、幂等与状态冲突
- **THEN** `compose-smoke` 只承载跨容器主链路与关键契约校验，至少覆盖登录、鉴权、开放 API、关键管理接口和一条代表性业务路径，不承担替代模块级细节断言的职责
- **THEN** 人工验收 checklist 必须承接自动化测试未完全覆盖的视觉布局、复杂联动、运维配置、证书/Secret 挂载、文档一致性和外部联调体验，并要求逐项记录执行人、日期、环境与结论

#### Scenario: 定义各功能域的最小交付映射
- **WHEN** 团队拆分剩余功能点的测试与交付责任
- **THEN** `ETL/CDM` 至少应具备抽取配置/映射校验的后端模块测试、主题级 smoke 入口和人工核对样例预览/下游复用结果的步骤
- **THEN** 报表设计器至少应具备布局与筛选解析的前端交互测试、模板版本/发布规则的后端模块测试，以及人工核对预览/导出/调度一致性的步骤
- **THEN** 开放 API 至少应具备参数契约、权限/scope、脱敏、错误码与日志口径的后端模块测试，`compose-smoke` 或 `.http/Postman` 联调入口，以及人工核对外部文档示例的步骤
- **THEN** 系统/安全治理至少应具备菜单/动作/数据范围/字段权限协同的前后端测试、`prod` 安全基线自检入口和人工核对密钥轮换/Secret 挂载/启动失败口径的步骤

#### Scenario: 提升覆盖率门禁并保留失败制品
- **WHEN** 团队为剩余功能持续提升验收级测试强度
- **THEN** 当前最小门禁 `frontend` `statements/functions/lines >= 8`、`branches >= 5` 与 `backend` `line >= 10%`、`branch >= 5%` 只能作为下限，不得因新增功能回退
- **THEN** 覆盖率提升方向冻结为：优先对新增功能所在模块补齐测试，再逐步把 `frontend` 门禁提升到 `statements/functions/lines >= 12`、`branches >= 8`，把 `backend` 门禁提升到 `line >= 15%`、`branch >= 8%`；未达到提升条件前，合并请求至少不得降低现有阈值或覆盖结果
- **THEN** 任一测试失败都必须保留对应制品：后端保留 `backend/target/surefire-reports/` 与 `backend/target/site/jacoco/`，前端保留 `frontend/coverage/`，容器回归保留 `.artifacts/compose-smoke/`，并在 `docs/交付验证记录.md` 中记录失败阶段与复现入口
- **THEN** 回归入口必须统一指向 `backend` 的 `mvn clean verify`、`frontend` 的 `npm run check:ci`、仓库根目录的 `pwsh ./scripts/docker-smoke.ps1` 与 `tests/api/medical-data-center-smoke.http` / `tests/postman/MedicalDataCenter.postman_collection.json`，避免不同文档给出互相冲突的执行方式

#### Scenario: 同步更新交付文档责任
- **WHEN** 任一剩余功能完成实现、联调、验收或回归失败修复
- **THEN** 功能实现责任人必须同步更新 `docs/部署文档.md`、`docs/使用手册.md`、`docs/API接口说明.md`、`docs/交付验证记录.md`、`docs/项目进度说明.md` 中受影响的章节；若能力未触及某文档，提交说明中也必须显式标注“不涉及”
- **THEN** 文档更新责任划分固定为：实现责任人更新功能说明与执行步骤，测试/交付责任人补充验证结论与失败制品位置，评审人复核规格、代码、文档三者状态一致
- **THEN** 任何新增接口、参数、权限规则、部署前置条件、回归入口、端口、制品目录或当前态版本号发生变化时，都必须在同一提交窗口完成文档同步，不得把文档修正延后到后续批次
- **THEN** 若 `spec.md`、`tasks.md`、`checklist.md` 与交付文档出现状态冲突，以“代码与验证结果对应的最新真实状态”为准，并必须在当前任务中完成校正

#### Scenario: 生成完整功能验证 checklist
- **WHEN** 团队为所有剩余功能点整理最终验收清单
- **THEN** checklist 必须能逐项追溯到 `ETL/CDM`、报表设计器、开放 API、系统/安全治理、测试交付五大域，并覆盖功能点本身、异常处理、边界条件、自动化测试入口、人工验收步骤和文档同步状态
- **THEN** checklist 中与前序已完成任务对应的条目应在本轮 Task 6 收口时勾选完成；仅与 `/spec` 路径一致性复核直接相关的收尾项允许留待后续 Task 7 处理
- **THEN** checklist 至少应显式覆盖以下测试交付项：测试分层映射已建立、覆盖率门禁方向已定义、失败制品目录已固定、统一回归入口已声明、交付文档责任人已明确、所有剩余功能域均具备可执行验收路径

#### Scenario: 更新交付文档
- **WHEN** 任一剩余功能补全完成
- **THEN** 部署文档、使用手册、接口说明、交付验证记录、项目进度说明必须同步反映最新真实状态
- **THEN** 不得出现代码已实现而规格/文档仍显示缺失的情况

## MODIFIED Requirements
### Requirement: 后续阶段推进口径
系统 SHALL 从“按阶段完成一个最小增强闭环”升级为“对所有剩余未完成功能建立全面补全规格基线”，后续实现可继续按模块或阶段执行，但必须遵守本次冻结的剩余范围与接口契约。

#### Scenario: 后续实现团队读取规格
- **WHEN** 开发、测试或交付人员开始处理剩余模块
- **THEN** 应以本次规格中定义的剩余能力清单、接口与边界为准
- **THEN** 既有已完成规格仅作为历史收口记录，不再承担新增剩余能力定义职责

### Requirement: 规格文档一致性
系统 SHALL 保持 `/spec` 路径下历史规格与当前补全规格之间的状态一致性：历史规格标记“已完成收口”，新规格承担“剩余能力补全基线”角色。

#### Scenario: 审阅 `/spec` 路径
- **WHEN** 团队在 `/spec` 目录中回溯项目规格
- **THEN** 应能区分“已完成阶段规格”和“当前剩余能力规格”
- **THEN** 不同规格之间不得对当前实现状态或后续优先级给出相互冲突的描述

## REMOVED Requirements
### Requirement: 剩余功能仅保留原则性描述
**Reason**: 现有历史规格更多聚焦阶段性收口，已不足以支撑剩余模块的详细设计与验收。
**Migration**: 后续剩余能力一律在本规格中补足技术方案、接口定义、交互逻辑、异常处理与 checklist，再据此进入实现。
